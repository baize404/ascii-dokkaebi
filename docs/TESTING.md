# 測試結果、效能、相容性與已知限制（3.0）

> **4.0 起**：純 3D，ASCII 渲染已移除。4.0 的測試結果、效能與錄影見 [docs/v4/TESTS.md](v4/TESTS.md)；本文件以下是 3.x（ASCII 版）的紀錄，保留作為比較。

> 本文件的數字都來自實際執行的結果。測試環境沒有實體顯示卡、沒有真實手機，也沒有真人玩家；這些限制都在下面標明，沒有測過的就寫「未測試」。

## 測試環境

- Linux 容器（2 核心 CPU）、Node.js 22、Google Chrome（無頭模式）
- WebGL 由 **SwiftShader** 用 CPU 模擬，沒有實體顯示卡
- 桌面 1280×800；手機直式 390×844（DPR 2、觸控）；手機橫式 844×390（DPR 2、觸控）
- 指令：`npm test`、`npm run build`、`npm run test:e2e`、`node tests/e2e/blackbox.mjs`、`node tests/e2e/record.mjs`、`node tests/e2e/perf.mjs`

**怎麼解讀**：

- 在這個環境裡，**原始 3D 和各種 ASCII 模式一樣慢**。所以主要成本是 3D 場景本身（陰影、燈光、骨架角色），ASCII 的三個 pass 不是瓶頸。字元密度從 Classic 提高到 Cinematic，格數增加約 9 倍，幀率只差約 15%。
- 畫質「低」：關閉陰影、降低 DPR 與草叢、粒子數量。手機尺寸從約 6 FPS 提升到 18–21 FPS，是最有效的降負擔方式，自適應畫質會優先使用它。
- Hybrid 比 HD 多一個連續光暈的取樣，是 ASCII 模式中最慢的；Pure ASCII 最快。
- JS heap 穩定在 20–45 MB，沒有隨模式切換持續增加。
- **這些不是真實裝置的數字。** SwiftShader 用 CPU 模擬整張顯示卡，通常比一般筆電或手機的 GPU 慢一個數量級以上。計畫的目標（一般筆電標準模式約 60 FPS、中階手機 30 FPS 以上）**尚未在真實硬體上驗證**。

**主要 GPU 瓶頸（依程式分析，未在實機用 profiler 確認）**：即時陰影貼圖（每幀多渲染一次場景）、骨架蒙皮（4 個角色、每個 27–40 根骨頭）、半透明粒子與草叢的 overdraw。

**效能相關的設計**：

- 字元密度、場景取樣、DPR、陰影解析度分開設定。
- 場景貼圖有上限：超過時自動降取樣。
- 自適應畫質有遲滯與冷卻時間，撐不住的等級會被暫時封鎖，畫質不會來回跳動。
- 遠處的 NPC 降低動畫更新頻率。
- 草、落葉、屋瓦、石牆用 InstancedMesh。
- 粒子使用物件池。
- 重新開始時釋放整個場景的幾何與材質；ASCII 的 Render Target 整個遊戲共用，只在畫面尺寸或密度改變時調整大小。

## 7. 已知限制

1. **真實裝置的效能沒有量測**。只有 SwiftShader 的相對數字；計畫中「一般筆電 60 FPS、中階手機 30 FPS」的目標尚未驗證。
2. **Firefox、Safari、iOS Safari、Android 實機都沒有測試**（見第 6 節）。
3. **沒有真人測試**。黑箱測試是 AI 模擬玩家，它的推理規則是人寫的，無法代表真人會卡住的地方，例如看不懂畫面、誤解提示。
4. **人物面數低於計畫的初始預算**。主角約 11,800 面（計畫建議 15k–35k）。在 ASCII 畫面中額外的面數看不出差別，所以預算優先花在關節輪廓。3D 模式的特寫還有提升空間，例如手指只有一節、臉部是幾何零件。
5. **只有廚房可以走進去**。倉庫的門會開，但不能進去；할머니家只能從門口看屏風；其他房子是外觀模型。
6. **窗戶不能開關**。DoorController 也能用在窗戶，但目前只有門使用它。
7. **池塘倒影是在著色器裡畫出月亮與光點**，不是真的鏡面反射（沒有用 Reflector 再渲染一次場景，這是為了效能）。
8. **局部高密度字元渲染沒有做**。改用近景與調查特寫鏡頭讓重要物件在畫面上變大（計畫 4.7 允許的替代方案）。
9. **錄影是逐格渲染**。動作流暢度是真的動畫系統輸出，但不代表實際幀率。
10. **黑貓的煙霧轉場**：黑貓換地點時是跳起來化成一陣煙，不是走過去。
