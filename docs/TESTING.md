# 測試結果、效能與已知限制

## 測試環境

- Linux 容器、Node.js 22、Google Chrome（無頭模式），WebGL 由 **SwiftShader 軟體模擬**（沒有真實顯示卡）。
- 桌面 1280×800；手機直式 390×844（DPR 2、觸控）；手機橫式 844×390（DPR 2、觸控）。
- 指令：`npm test`、`npm run build`、`npm run test:e2e`。

## 效能量測

### 在 SwiftShader（軟體模擬顯示卡）上的實測

| 畫面 | 畫質「高」 | 畫質「低」 | JS heap |
| --- | --- | --- | --- |
| 桌面 1280×800 | 6.4 FPS | 9.0 FPS | 22–23 MB |
| 手機 390×844 @2x | 6.6 FPS | 21.7 FPS | 22–26 MB |

**這不是真實裝置的數字。** SwiftShader 用 CPU 模擬整張顯示卡，速度通常比一般手機的 GPU 慢一個數量級以上。這組數字只能證明兩件事：畫質設定確實能大幅降低負擔（手機尺寸從 6.6 → 21.7 FPS），以及執行期記憶體穩定在約 25 MB。

**計畫中的效能目標（桌面接近 60 FPS、中階手機 30 FPS 以上）尚未在真實裝置上驗證。** 遊戲內「設定 → 畫面 → 顯示 FPS」可以直接查看實際幀率，「畫質：自動」會在幀率持續低於 40（高→中）或 26（中→低）時自動降級。

### 為效能做的設計

- 3D 場景只渲染到「字元格數 × 2」的小貼圖（1280×800 約 320×200 像素），全螢幕只跑一次 ASCII shader。
- 畫質等級控制：陰影（關／1024／2048）、像素比上限（1／1.5／2）、草叢數量（35%／70%／100%）、粒子數量、螢火蟲數量。
- 草、落葉、踏腳石、屋瓦、石牆都用 InstancedMesh。
- 粒子用固定大小的池，不產生垃圾回收；重新開始時整個場景 dispose。
- 打包大小：JS 約 745 KB（gzip 後約 200 KB，大部分是 Three.js）。

## 已知限制

1. 真實裝置的幀率尚未量測（只有 SwiftShader 數字）。
2. 音效與音樂在無頭測試中無法「聽」，只驗證了不會出錯；音量平衡需要實際戴耳機調整。
3. 尋路是 0.5 公尺網格；角色會沿網格拉直後的路線走，極窄的縫隙可能判定為不可通行。
4. 鏡頭遮擋處理是「拉近並升高」，不會把擋住的屋頂變透明。
5. 民俗圖鑑的內容依網路公開資料（主要是 Wikipedia 與韓國政府網站）改寫，未經民俗學者審閱。
6. 存檔只存在同一個瀏覽器的 localStorage，換裝置或清除網站資料就會消失。

## 尚未完成的功能與後續建議

- **真實裝置效能驗證**：用幾支不同等級的手機實際遊玩，依結果調整自動畫質門檻。
- **更多 NPC 與支線**：例如可以和도깨비比씨름（摔角）的小遊戲。
- **多語系**：所有文字已集中在 `src/data/`，可以加上英文或韓文版本。
- **打包分割**：把 Three.js 拆成獨立檔案，改版時玩家不需要重新下載。
- **雲端存檔**：目前刻意不加入登入系統與後端服務；若之後需要跨裝置存檔再評估。
- **專業審閱**：請熟悉韓國民俗的人審閱圖鑑內容與劇情用詞。
